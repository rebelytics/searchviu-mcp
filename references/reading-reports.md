# Reading report output — derived columns, metadata, facets and field semantics (§7–§10)

## 7. Figures that don't reconcile — suppress rather than caveat

Some derived columns cannot be interpreted through the API at all. On the
platform's global issues report, the issue table carries an affected-URL
count plus two share columns, and its subtitle states the displayed
dynamic risk rating is derived from them — so they drive a priority, they
are not decorative. Dividing count by share yields an implied denominator
that is perfectly consistent across rows within one response, and that
**grows as the filtered population shrinks** (~5% across three
progressively narrower crawl-date scopes, moving monotonically the wrong
way). Whatever the shares are proportions of, it is not the filtered set.
The affected-URL counts respond correctly to `crawl_date` filtering and
can be used; the share columns and the risk rating derived from them
cannot, and should be read off the UI or omitted.

Generalise the test rather than memorising the case: **vary the query
scope and check that every derived quantity moves in the direction the
arithmetic requires.** Internal consistency within one response is not
evidence of correctness — a column can agree with itself on every row and
still be computed against the wrong population. Where a displayed priority
or severity is derived from such a column, the defect propagates into a
recommendation, so unexplained arithmetic is a reason to suppress the
figure, not to footnote it.

Two related quirks found on the same report, worth carrying as habits:
the unfiltered issue table returned 77 rows for 76 distinct
`issue_keyword` values, i.e. **a cross-crawl aggregate is not de-duplicated
on its own key column, so a row count is not an entity count**; and the
`multifilter_bar` widget returned `rows: []` in every call despite
declaring a `crawlSelector` in its config, so that facet provided no
crawl-date enumeration through the API — the crawl scopes had to be found
by probing ranges.

## 8. Report metadata is a claim, not a spec

A report response carries two classes of content. **Behaviour** — widget
config, returned columns, returned rows, `totalRows` — is generated by the
query. **Claims** — report name, description, column labels — are
human-authored and merely travel in the same envelope. Only the first is
evidence of what the report does. Observed after a filter fix: three
rebuilt reports whose descriptions still asserted the removed condition as
active ("Live = <field>=true AND status=200") while rows came back with
that field `false` — the description stating the opposite of the report's
behaviour; and a description claiming a distinct *entity* count while the
widget config performed `count_distinct` on a *URL* column and its own
label said "URL count (distinct)".

A description is evidence of *intent at authoring time*, never of current
behaviour — and it is the artefact least likely to be updated when a query
is fixed, precisely because fixing the query is the urgent part, so the
gap between them only ever widens. Where description and rows disagree,
the rows win, and the drift is worth reporting back to whoever owns the
report. Never quote a description's stated scope into a deliverable;
confirm it against the returned rows first.

## 9. Facet widgets are self-excluding — never read absence off a facet list

Reports return a filter-bar (multifilter) widget listing each dimension's
values with counts, alongside the data table. When a filter is applied on
dimension D, the facet list for D keeps showing the **full unfiltered
value set** (standard faceted-search behaviour: a facet shows what you
could switch to), while other dimensions' facets filter normally. Read
carelessly, this looks like the filter was ignored.

- To answer "does value V of dimension D occur": read the **data table's
  `totalRows`**, never the facet list for D.
- The useful inverse: the **unfiltered** facet list for D is the cleanest
  one-call enumeration of D's distinct values, and a value absent from
  that list is strong evidence it never occurs.

## 10. Field semantics — sentinels, the inlink_count family, and extraction keys

**A crawler-recorded value is a claim about what the crawler received, not
about what the server sends to the clients a fix is for.** Two fields carry
this in practice. `crawl_http_status` on `http://` URLs: a **307** recorded on
the http→https hop is a value to live-check with a plain HTTP client before
it is reported as a site defect — one request per URL, once with a browser
user agent and once with a search-engine bot user agent, reading the first
hop's status. The failure shape: a set of legacy `http://` product URLs
recorded at 307 across consecutive crawls answered 301 live to both
user agents, so the ticket point "fix the 307s" would have asked a dev team
to repair a redirect that was already correct; what produces the crawler's
307 is not established (the crawler's own scheme upgrade is one candidate).
The wider scope: **any renderer-recorded value** — a JavaScript console
error, a failed request, a rendered-vs-raw difference — is reproduced once
in a clean browser that starts from the same empty state (no cookies, no
storage) before it is reported as a defect or ranked as a lever. The failure
shape: a report ranked "JavaScript console errors" as the second-largest
lever on a site, with tens of thousands of pages sharing one first error — a
CORS preflight failure on a consent-management file — while a fresh browser
on a first visit passed the preflight and logged no console error. The
clean-browser condition is the point: a returning visitor's browser often
never makes the call the crawler makes on every page, so a casual check in
the user's own browser is not a reproduction either. Report what was
reproduced, by which client, and treat the remainder as a crawler artefact
to raise with the platform owner.

**`crawl_depth = 9990` (numeric, in the links source) is the same value as
`"Not linked internally"` (string, in the URL source), and it means zero
*followed* internal inlinks** — a statement about the link graph, not a
crawl failure. Pages carrying it were fetched successfully and returned
200. The same field can be typed differently across data sources, and
**the labelled variant is the place to resolve a sentinel's meaning** —
one call against the string-typed source decodes it definitively. When a
numeric field carries an obviously out-of-range value, look for a second
representation of the same field before inventing an interpretation: a
plausible guess about a sentinel is agreed to once and then silently
governs everything downstream.

Three riders that make the flag — and every inlink count — usable:

- **In a multi-domain project, "internal" spans every domain in the
  project.** The link graph is built per project, not per host, so a link
  from one of the project's domains to another is an internal link — and a
  language/country switcher on a sister domain is exactly such a link: a
  **non-paginated**
  inlink to every localised counterpart, from every other domain in the
  project. The failure shape: a product reachable only through pagination
  on its own domain shows a healthy non-paginated inlink count, and most of
  those inlinks are switcher links from sister domains — a floor every
  product on every domain receives, so no product in the project falls
  below one non-paginated source. To a search engine those are links
  between separate sites: they aid discovery but are not the target
  domain's own internal linking, and they are not the safety net that makes
  pruning pagination safe. So **split inlink counts into same-domain and
  cross-domain sources before any linking-dependence or orphan conclusion**
  — compare the host of `url_from` with the host of `url_to`, client-side on
  a bulk pull or through a `url_from like "<host>/"` probe per domain — and
  state which of the two a quoted figure is. The `inlinks_from_paginated` /
  `inlinks_from_non_paginated` aggregate columns do not make this split.
  The mirror-image caveat when reconciling against another tool: a
  single-domain crawl cannot see these links at all, so the two instruments
  disagree by construction, not because one is wrong — check what each
  one's boundary includes before asking which is right.
- **`inlink_count` counts canonical, hreflang and nofollow references
  too.** Rows filtered to `"Not linked internally"` came back with
  `inlink_count` of 2 or 3 alongside `inlink_count_follow: 0` — linked,
  but with no followable path. The family (`inlink_count`, `_follow`,
  `_nofollow`, `_canonical`, `_href_lang`) decomposes this; any orphan or
  internal-linking analysis must use `inlink_count_follow`.
- **The flag's population is mixed by discovery source.** The URL table
  holds URLs found by traversal alongside URLs imported from other
  sources (Search Console, feeds, previous crawls), and a URL known only
  from an external source always carries the no-internal-link flag —
  correctly, and uninterestingly. Often only a minority of the flagged live
  URLs are in the XML sitemap, and the rest are deliberately unlinked items
  such as promotions. An independent inventory of what *should* be linked
  is required to make the flag mean anything — the data source usually
  carries one (`xml_sitemap_contains_url`).

**Extraction fields used as join or grouping keys must be probed across
markets before any cross-market report is built on them.** An extraction
that captured a localised display label instead of the adjacent stable ID
matches its source perfectly on every single-market spot-check — the
defect only appears across markets, where the same term renders under a
different label per domain, so the stored value encodes market × concept
rather than concept. Verifying an extraction against its source proves it
*reads* correctly, not that the *right field* was captured. Two cheap
probes settle it, one call each: search the stored values for structural
characters from the source object to confirm what was retained, and
search for a known translated form of a term whose canonical form is
already present. (The upstream fix — extract the identifier, keep the
label as an additional field — belongs to the extraction config, not to
the query.)

**A row's single date field need not describe every payload in that row.**
On the global Prompt Tracking report, `latest_data_week` and
`last_result_date` carry the last week in which **all** engines ran, while
the `ai_answers` payload is **per-engine latest**. When the engines are out
of step the two disagree inside one row and nothing in the row says so:
observed with every row reporting one `latest_data_week` while two of
three engines' answers in those same rows were headed the following week, so
any own-brand flag read beside the answer text was a verdict from one week
sitting next to an answer from the next. Each answer block carries its own
date header — **parse the date off each payload, not off the row**, and
treat the row's finding line, own-brand flags and week label as belonging to
`latest_data_week` only. The Changes report is engine-aware and handles this
correctly for trends; the per-prompt report does not label it. Full account
in `searchviu-tracking-strategy-builder`.
